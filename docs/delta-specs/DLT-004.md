# Delta Spec: DLT-004 - Open web pages in browser tabs

## Story

As a developer using seemux, I want to open web pages inside browser tabs so that I can view documentation or web content alongside my terminal sessions without leaving the application.

## What It Does

Adds a new session type — "browser" — that runs a terminal-based browser (e.g., Carbonyl) inside a VTE terminal widget. Browser sessions display a distinct icon, URL, and page title in the sidebar instead of folder/CWD metadata. They are created via a keybinding (with a URL input modal) or by right-clicking a detected URL in another terminal. When the browser process exits, the session closes entirely. The current URL is tracked as the user navigates and persisted for restoration on restart.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Sessions support a type distinction (shell vs browser) so they can be created, displayed, and managed differently | Core goal |
| R1 | Browser sessions render web pages using a terminal-based browser (fixed binary, research best tool in design phase) | Core goal |
| R2 | Browser sessions display browser-appropriate metadata in sidebar: URL, page title, distinct icon | Must-have |
| R3 | Browser tabs created via keybinding (modal with blank URL input) or right-click on detected URL | Must-have |
| R4 | Browser sessions participate in the session system — sidebar, groups, notifications | Must-have |
| R5 | Browser sessions persist across restarts; current URL is saved and browser re-spawned with it | Must-have |
| R6 | Browser sessions participate in layouts alongside shell sessions | Must-have |
| R7 | When browser process exits, session closes entirely (no fallback to shell) | Must-have |
| R8 | Browser binary is fixed — not configurable | Must-have |
| R9 | Track URL changes as the user navigates; persist current URL for restoration | Must-have |

## Acceptance Criteria

### Session Type (R0, R4)

- [ ] Given the session model, when a session is created, then it has an explicit type (Shell or Browser) that determines its lifecycle, display, and spawning behavior
- [ ] Given a browser session, when listed in the session manager, then it participates in all session operations: group assignment, sidebar display, tab switching, drag-and-drop, notifications
- [ ] Given a browser session, when the user switches tabs, then it activates like any other session

### Browser Rendering (R1, R8)

- [ ] Given a browser session with a URL, when created, then the fixed terminal-based browser binary is spawned inside the VTE terminal with that URL as an argument
- [ ] Given the browser binary is not found on the system, when a browser session is attempted, then the user is informed with an error message and no session is created
- [ ] Given the browser binary is found but fails to start (permissions, missing dependency), when spawn fails, then the user is informed with an error message and no session is created
- [ ] Given a browser session, when the browser process renders content, then it displays inside the VTE terminal widget just like a shell session

### Sidebar Display (R2)

- [ ] Given a browser session tab row, when displayed in the sidebar, then it shows a globe icon instead of the folder icon (specific icon chosen in design phase)
- [ ] Given a browser session tab row, when displayed in the sidebar, then the title shows the page title (or the URL if no page title has been reported yet)
- [ ] Given a browser session tab row, when displayed in the sidebar, then the subtitle shows the current URL
- [ ] Given a browser session, when the page title or URL changes, then the sidebar tab row updates accordingly (even when the session is not focused)
- [ ] Given a browser session, when git branch/PR detection runs, then it is skipped for browser sessions (no git metadata displayed)

### Browser Tab Creation (R3)

- [ ] Given the user presses the browser keybinding, then a URL input modal appears with a blank text field
- [ ] Given the URL input modal, when the user types a URL and submits, then a browser session is created with that URL
- [ ] Given the URL input modal, when the user submits a URL without a protocol (e.g., "example.com"), then "https://" is prepended automatically
- [ ] Given the URL input modal, when the user presses Escape or Cancel, then the modal is dismissed and no session is created
- [ ] Given the URL input modal, when the user submits with empty input, then the modal is dismissed and no session is created
- [ ] Given the user right-clicks on a detected URL in a shell session terminal, then the context menu includes an "Open in browser tab" option
- [ ] Given "Open in browser tab" is clicked on a URL, then a browser session is created with that URL

### Persistence (R5, R9)

- [ ] Given a browser session with URL "https://example.com/page", when state is saved, then the session type, current URL, and page title are persisted
- [ ] Given saved state containing a browser session, when seemux restarts, then the browser session is restored and the browser re-spawned with the saved URL
- [ ] Given a browser session where the user navigated to a new URL, when state is saved, then the latest URL is persisted (not the original)
- [ ] Given a saved state file from before browser sessions existed (no session_type field), when loaded, then all sessions default to Shell type and load correctly
- [ ] Given a restored browser session, when the browser binary is no longer available on the system, then the session is skipped with a warning logged and other sessions restored normally

### Layout Participation (R6)

- [ ] Given a browser session and a shell session, when a layout is created, then both session types can be arranged side-by-side
- [ ] Given a browser session, when split/pane operations are available, then browser sessions participate in the same layout rules as shell sessions

### Session Lifecycle (R7)

- [ ] Given a browser session where the browser process exits (user quits, crashes, or is killed), then the session is destroyed immediately — all exit reasons are treated identically with no fallback to shell
- [ ] Given a browser session is destroyed, then focus moves to the next appropriate session following the standard tab destruction rules

## User Flow

### Breadboard: Open Browser Tab

```
  Terminal (shell session)
  ------------------------
  - right-click on URL
  - "Open in browser tab" menu item
       |
       v
  Browser Tab (new session)
  -------------------------
  - VTE terminal rendering browser
  - sidebar shows browser icon + page title + URL
  - URL updates as user navigates
       |
       v
  Browser Exits
  -------------
  - session closed
  - focus moves to next tab
```

### Breadboard: Open Browser Tab via Keybinding

```
  Any Tab
  -------
  - browser keybinding pressed
       |
       v
  URL Input Modal
  ---------------
  - blank URL text field
  - [Open] button
  - [Cancel] button
       |
  +----+----+
  |         |
  v         v
  Browser   Any Tab
  Tab       -------
  (see      (no change)
  above)
```

### Flow Description

**Entry point**: User either (a) right-clicks on a detected URL in any terminal and selects "Open in browser tab", or (b) presses the browser keybinding to open the URL input modal.

**Happy path (right-click)**: User right-clicks a URL → context menu appears with "Open in browser tab" → user clicks it → browser session is created with that URL → browser renders inside the VTE terminal → sidebar shows browser icon, page title, and URL.

**Happy path (keybinding)**: User presses keybinding → URL input modal appears with blank field → user types URL and presses Enter → browser session is created → same rendering and sidebar behavior as above.

**Decision points**:
- Modal: submit vs cancel/escape — cancel or escape dismisses without creating a session
- Empty URL input: modal is dismissed without creating a session
- URL without protocol: "https://" is prepended automatically
- Browser binary not found: error message shown, no session created

**Exit points**:
- Browser process exits → session destroyed, focus moves to next tab
- User closes the session via Ctrl+Shift+W → same destruction behavior

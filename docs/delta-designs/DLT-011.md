# Design: DLT-011 - Clear notification badge on tab activation and session cleanup

**Delta Spec**: [../delta-specs/DLT-011.md](../delta-specs/DLT-011.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Notification badges are only cleared when callers explicitly invoke `NotificationStore::mark_read` after calling a switch method. This means badge clearing depends on every activation path remembering to call `mark_read` — and several paths don't. Additionally, `destroy_session` clears notification state *after* removing the sidebar tab, causing a brief window where the badge count is nonzero for a tab that no longer exists.

The scattered `mark_read` calls create a maintenance burden: any new activation path must remember to add the call, and the 8 existing call sites in `keyboard.rs`, `app/mod.rs`, and `dropdown.rs` each duplicate the same logic.

Constraints:
- GTK's single-threaded event loop means all mutations happen on the main thread — no concurrency concerns
- `NotificationStore` uses `Rc<RefCell<>>` (ADR-002), consistent with the rest of the codebase
- The dropdown's `mark_read` in `show()` serves a different purpose (window visibility, not tab activation) and must remain independent

## Design Overview

Centralize badge clearing into `SessionManager::switch_to` so that every tab activation automatically dismisses the target session's badge, then remove the now-redundant `mark_read` calls from all external callers. Additionally, reorder `destroy_session` to clear notification state before removing the sidebar tab, ensuring the badge transitions cleanly to zero before the row is removed.

The design follows DES-002 (callback-based event wiring): `switch_to` is the single activation funnel, and adding `mark_read` there means all callers benefit automatically.

### Cross-Layer Contracts

**NotificationStore::mark_read contract**:
- Input: `session_id: &str`
- Effect: Sets unread count to 0, fires `on_change(session_id, 0, latest, total)`
- If session not in store: silently inserts entry with count 0 and fires `on_change` — no panic, no error. This is acceptable for new sessions that start with zero notifications.
- Called synchronously within GTK main loop (single-threaded, per ADR-002)

**NotificationStore::clear_session contract**:
- Input: `session_id: &str`
- Effect: Removes both `unread_count` and `latest_notification` entries, fires `on_change(session_id, 0, None, total)`
- Removes the session entirely from the store (vs. `mark_read` which keeps the entry with count 0)

**on_change callback contract** (DES-002):
- Signature: `Fn(session_id: &str, count: u32, latest: Option<&Notification>, total: u32)`
- Fires synchronously during `mark_read` or `clear_session`
- Used by: sidebar badge update, system tray count update
- Must not panic (runs within GTK main loop; a panic would crash the application)

**Integration Points**:
- `switch_to` already holds `notification_store` via `self` — no new parameters needed
- All callers of switch methods (`switch_adjacent`, `switch_to_index`, `switch_to_visible_index`, etc.) funnel through `switch_to`, so centralization is automatic

### Shared Logic

No new shared logic. The existing `NotificationStore::mark_read` method is the shared clearing mechanism — this delta just moves *where* it's called.

### Entities and Relationships

```

  id: String      │
  status: Enum    │  1:N
  group_id: String│────── NotificationStore
                  │        unread_count_by_session: HashMap<String, u32>
                  │        latest_by_session: HashMap<String, Notification>
                  │        on_change: callback
                  │
                  └──── TabRow (sidebar widget)
                           badge: shows unread_count
                           Updates via on_change callback
```

### Badge State Transitions

```
                    add_notification()
   [No entry] ──────────────────────► [Notified: count > 0]
        ▲                                    │
        │                    mark_read()     │
        │               ◄───────────────────┘
        │                                    │
        │              clear_session()       │
        │         ◄──────────────────────────┘
        │
        └── (session destroyed, entry removed)
```

Key invariant: `badge count is zero iff no unread notifications exist for the session`.

After DLT-011:
- `mark_read()` fires automatically on every tab activation via `switch_to`
- `clear_session()` fires before sidebar removal during `destroy_session`
- The only `mark_read` outside `switch_to` is the dropdown's `show()` — a window visibility event, not tab activation


## Key Decisions

### Centralize in `switch_to` rather than a wrapper or signal

**Choice**: Add `mark_read` directly inside `switch_to`
**Why**: `switch_to` is the single funnel through which all tab activation flows. Every navigation method (`switch_adjacent`, `switch_to_index`, etc.) and every external caller (sidebar click, keyboard handler, hook command, editor activation) ultimately calls `switch_to`. Verified in the Activation Path Verification table above — all 13 paths confirmed.
**Alternatives Considered**:
- GIO action for badge clearing: Would add indirection for a single method call; DES-004 (GIO action dispatch) is for UI commands with menu/shortcut bindings, not internal state updates
- GTK signal on the Stack's `notify::visible-child`: Would couple badge clearing to widget internals; `switch_to` does more than just change the visible child (it also spawns restored panes, sets sidebar active, grabs focus)

**Consequences**:
- Pro: Every activation path automatically clears badges — no path can be missed
- Pro: Eliminates 8 duplicated `mark_read` calls across 3 files
- Con: `switch_to` now has a side effect (notification clearing) that wasn't there before — but this is the intended behavior per the spec

### Place `mark_read` after `set_active` in `switch_to`

**Choice**: Call `notification_store.borrow_mut().mark_read(session_id)` after `self.sidebar.set_active(session_id)` but before `grab_focus`
**Why**: The `mark_read` call triggers `on_change`, which updates the sidebar badge. Doing this after `set_active` means the sidebar already knows the tab is active (for visual highlighting), and the badge update is a follow-up state change. Placing it before `grab_focus` keeps the notification clearing within the "activation logic" portion of the method, separate from the "focus terminal" portion.
**Alternatives Considered**:
- Before `set_active`: Would update badge before the tab is visually active, causing a brief state mismatch in the sidebar callback
- After `grab_focus`: Would work functionally but is less readable — the notification clearing should be grouped with activation, not with focus

**Consequences**:
- Pro: Clear ordering within the method: activate → clear badge → grab focus
- Pro: Sidebar's `on_change` callback sees consistent state (tab is active, badge is cleared)

### Move `clear_session` before `remove_tab` in `destroy_session`

**Choice**: Reorder so `clear_session` runs first
**Why**: The `on_change` callback on `NotificationStore` updates the sidebar badge and system tray count. If `remove_tab` runs first, the sidebar row is gone and the badge update has no target — the tray count may also briefly show a stale total. Clearing first ensures the badge transitions to zero while the row still exists, then the row is removed.
**Alternatives Considered**:
- Keep current order and accept transient inconsistency: Simpler but leaves a brief visual glitch
- Add a separate pre-destruction hook: Over-engineered for this simple reordering

**Consequences**:
- Pro: Clean badge-to-zero transition before row removal
- Pro: System tray count decrements correctly before the session is gone

### Leave dropdown's `mark_read` unchanged

**Choice**: The `mark_read` call in `Dropdown::show()` (`dropdown.rs:189`) remains as-is
**Why**: The dropdown's `mark_read` handles the case where the user reveals a hidden window without changing which tab is active. `switch_to` is NOT called because the active session doesn't change — only window visibility changes. This is semantically different from tab activation: the user isn't switching tabs, they're revealing an already-active tab in the dropdown overlay.
**Alternatives Considered**:
- Remove it and rely on `switch_to` centralization: Would break dropdown badge clearing since `show()` doesn't call `switch_to`

**Consequences**:
- Pro: Dropdown behavior unchanged, no regression risk
- Con: One remaining `mark_read` outside `switch_to` — but it's semantically different (window visibility vs. tab activation)

## System Behavior

### Scenario: User clicks sidebar tab with notifications

**Given**: Session B has 3 unread notifications
**When**: User clicks Session B's sidebar tab row
**Then**: `switch_to(B)` is called → `mark_read(B)` fires → badge clears → terminal gets focus
**Rationale**: Single path, no scattered `mark_read` needed

### Scenario: Keyboard shortcut switches to tab with notifications

**Given**: Session C has 1 unread notification, Session A is active
**When**: User presses Ctrl+Tab (which triggers `switch_adjacent`)
**Then**: `switch_adjacent` calls `switch_to(C)` → `mark_read(C)` fires → badge clears
**Rationale**: Keyboard handler no longer needs its own `mark_read` — the centralization handles it

### Scenario: Closing a tab with notifications focuses adjacent tab

**Given**: Session A is active with 2 notifications, Session B is adjacent
**When**: User closes Session A
**Then**: `destroy_session(A)` runs: `clear_session(A)` clears A's state, `remove_tab(A)` removes the row, then `switch_to(B)` runs and `mark_read(B)` clears B's badge
**Rationale**: Both sessions cleaned up correctly — destroyed session via `clear_session`, new focus target via `switch_to`

### Scenario: focus-session hook command

**Given**: Session D has notifications, a hook command targets it
**When**: `cmd_focus_session` calls `switch_to(D)`
**Then**: `mark_read(D)` fires automatically inside `switch_to`
**Rationale**: Hook commands get badge clearing for free — no code change needed in `hooks/commands.rs`

### Scenario: New tab created

**Given**: User creates a new tab via shortcut or menu
**When**: `register_session` calls `switch_to(new_id)`
**Then**: `mark_read(new_id)` fires — session is not yet in the store, so `mark_read` inserts a zero-count entry (harmless no-op). Any notifications that arrive later will be tracked normally.
**Rationale**: Defensive clearing for new sessions; `mark_read` is a no-op for sessions with no notifications

### Scenario: Session restored from saved state

**Given**: Sessions are restored on startup, active session index is set
**When**: `restore_session_with_splits` → `register_session` → `switch_to(restored_id)`
**Then**: `mark_read(restored_id)` fires for the restored active session
**Rationale**: Ensures badge is cleared even if notifications were somehow present during restoration

### Scenario: Dropdown window shown

**Given**: Dropdown is hidden, active session has notifications
**When**: User triggers dropdown toggle
**Then**: `Dropdown::show()` calls `mark_read(active_id)` directly — `switch_to` is NOT called because the active session doesn't change
**Rationale**: Window visibility event, not tab activation. The dropdown's `mark_read` remains independent.

### Scenario: mark_read called for session not in store

**Given**: A newly created session with no notifications
**When**: `switch_to` calls `mark_read(new_session_id)`
**Then**: `mark_read` inserts an entry with count 0 and fires `on_change` — badge stays at 0, no visual effect
**Rationale**: Harmless no-op. The `HashMap::insert` in `mark_read` handles missing keys gracefully.
